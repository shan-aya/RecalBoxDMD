## Page web de configuration (ESP32 WebServer)

- **Pas de limite de taille de page "dure" — c'est un risque probabiliste lié à la navigation rapide entre onglets.**
  `NetworkClient::write()` (bibliothèque Arduino ESP32, `cores/esp32/../Network/src/NetworkClient.cpp`) retente en interne jusqu'à 10x avec un `select()` d'1s chacun (~10-20s de blocage possible) si la connexion est abandonnée en plein transfert (ex. changement d'onglet avant la fin du chargement) — comportement **non configurable depuis le sketch** (`setTimeout()` testé et confirmé sans effet, `send()` utilise `MSG_DONTWAIT`). Pendant ce blocage, `loop()` entier est gelé (y compris le rendu DMD) — symptôme observé : affichage "parasité"/figé pendant ~20s après une navigation rapide entre pages de config.
  Historique : chassé en profondeur sur `master` (v45→v50, tests réels iOS/Nagle/heap), palier final = chunked-send (blocs 1Ko) + détection rapide d'échec partiel + garde heap `maxalloc<4096`. Le seuil **"~12.5 Ko à risque"** noté à l'époque est une heuristique empirique (page plus petite = fenêtre de transfert plus courte = moins de chance d'être interrompue), PAS un seuil technique dur. Reproduit à l'identique le 2026-08-20 sur `dev/core-reassignment` (page MEDIA, 13926o, bloquée 18.5s après navigation rapide) — confirme que cette limitation existe encore, inchangée, sur toutes les branches qui héritent de `sendGzipHtml()`.
  **Décision actée (2026-08-20, commit `edfd012`)** : réduire la taille des pages plutôt que patcher la lib vendue ou déplacer le traitement web. `BASIC` (19256o gzip, devenue la plus grosse après l'ajout hi-score) scindée en 2 : "Affichage" (luminosité + hi-score/infos/RA, 10691o) et "Playlist" (playlist + génération, 10004o) — nouvelle route `/config/playlist`. `MEDIA` (13928o) reste la page la plus grosse, non touchée cette fois — si un blocage s'y reproduit, candidate suivante pour une scission (ex. séparer upload GIF / gestion dossiers).

- **Patch vendored `Stream::timedRead()`/`timedPeek()` (2026-08-20, `dev/core-reassignment`) — TENTÉ PUIS ANNULÉ, NE PAS REFAIRE tel quel.**
  Constat initial : ces fonctions (Arduino core `cores/esp32/Stream.cpp`) busy-spinnaient sans `yield()`/`delay()`, causant un crash TASK_WDT réel quand `WebServer::_parseRequest()` les enchaîne sur un client HTTP lent. Fix tenté : `delay(1)` ajouté dans la boucle.
  **Effet réel constaté sur matériel : RÉGRESSION GRAVE.** Avant le patch, un blocage prolongé finissait par déclencher le TASK_WDT → crash + reboot automatique (perturbant mais auto-guérisseur, ~18-25s). Le `delay(1)` nourrit le watchdog en continu PENDANT le blocage, donc un blocage réseau qui aurait dépassé la tolérance de l'ancien mécanisme fait maintenant **geler le DMD indéfiniment**, sans auto-reboot — nécessitant un débranchement/rebranchement USB physique (survenu 2x le 2026-08-20 avant identification de la cause). Patch **REVERTÉ** (restauration depuis `_backups/Stream_2026-08-20_16-03-05.cpp.bak`), recompilé, reflashé, confirmé sain (brightness live testé OK).
  **Conclusion actée** : le crash TASK_WDT d'origine, bien que perturbant, jouait un rôle protecteur (auto-recovery) qu'un simple `delay()` supprime sans le remplacer par une vraie sortie de blocage. Ne pas réappliquer ce patch sans un mécanisme de timeout/abandon de connexion explicite en complément (pas juste nourrir le watchdog). Ce patch reste de toute façon HORS DU DÉPÔT GIT (installation Arduino partagée du poste de dev) — sans objet sur une autre machine tant qu'il n'est pas repensé.

- **`sendGzipHtml()` (pages de config web) n'envoyait AUCUN en-tete `Cache-Control` jusqu'au 2026-08-20.** Cause probable d'un symptome confus rencontre ce jour-la ("impossible de charger la config", listes non peuplees a l'ouverture) : un navigateur peut mettre en cache heuristiquement une reponse GET sans directive explicite -- sur un projet reflashe tres frequemment en developpement actif, une ancienne version de page (JS perime) peut alors rester servie depuis le cache alors que le format `/load` cote firmware a deja change, echouant silencieusement. Fix : `Cache-Control: no-store` ajoute a `sendGzipHtml()` (toutes les pages) -- a garder pendant toute la phase de developpement actif ; a reconsiderer seulement si/quand le rythme de changement de ces pages ralentit durablement.

## Architecture commandes MQTT firmware

- **`g_cmdPending[]`/tableau générique indexé par type de commande : DÉLIBÉRÉMENT ÉVITÉ.**
  Fortement suspecté de corruption mémoire (écriture hors-limites ailleurs dans le firmware atterrissant sur cette zone adjacente) sur la branche `dev/mame-score-mqtt-bridge` — expliquerait le bug "CMD_STARTCLIP fantôme" (déclenchement sans aucun message MQTT réel prouvable côté broker), jamais élucidé autrement malgré plusieurs sessions d'investigation. `dev/core-reassignment` utilise à la place `pendingCmd` (UN SEUL slot partagé, pas un tableau) + des variables dédiées nommées individuellement pour les commandes les plus sensibles (`g_pendingDefault`/`g_pendingSystem`+Arg/`g_pendingGame`+Arg) — motif à reproduire pour toute nouvelle commande MQTT plutôt que d'étendre un tableau générique.

- **rc=-4 / gels de connexion MQTT chassés sur plusieurs sessions : cause principale = overclock RPi5 + canicule, PAS le hi-score/LoopCore.**
  Confirmé le 2026-08-19 par test décisif (vitesse de navigation max, coupe-circuit anti-rafale désactivé, zéro rc=-4 une fois l'overclock retiré). Ne pas re-suspecter le portage hi-score ou la réassignation de cœur (`LoopCore=0`) pour CE symptôme précis sans nouvelle preuve — c'est un dossier distinct du bug "CMD_STARTCLIP fantôme" ci-dessus (qui, lui, reproduit indépendamment de l'overclock).

- **Coupe-circuit anti-rafale `marquee.sh` (`BURST_THRESHOLD`) — débit réel plafonne à ~5-7 survols/seconde sur ce matériel, PAS plus haut.**
  Mesuré à plusieurs reprises (2026-08-18 puis re-confirmé le 2026-08-22, `marquee_mqtt.log` agrégé + timestamps millisecondes serial DMD) : la navigation la plus rapide possible dans RB (y compris le mode "QuickJump" alphabétique) n'a jamais dépassé 6-7 survols dans la même seconde d'horloge. Un seuil fixé au-delà (`10`, testé le 2026-08-22) est structurellement inatteignable — le mécanisme (`!SHUFFLE`) ne se déclenche alors JAMAIS, symptôme silencieux (pas d'erreur, juste un no-op permanent). Valeur stable retenue : **`BURST_THRESHOLD=5`**, avec en plus (v16) une exigence de **durée soutenue** (`BURST_SUSTAIN_SECONDS=2`, secondes consécutives au-dessus du seuil) plutôt qu'un déclenchement instantané dès la 1ère seconde — évite un déclenchement visuellement trop précoce sur un simple pic isolé. Toute réintroduction/retouche future de ce mécanisme doit repartir de ces deux valeurs, pas de zéro.

- **Alertes de connectivité (verte "RecalBox connectée", orange "hors ligne", rouge "pas de wifi") — durée d'affichage 5s (`NO_WIFI_ALERT_DISPLAY_MS`/`MQTT_WAITING_MIN_DISPLAY_MS`), texte "connectée" en vert (2026-08-23, retour utilisateur, firmware v122).**
  Purement cosmétique/timing (ramené de 7s), aucun changement de logique de déclenchement. Règles de déclenchement complètes (rappel, voir aussi le code) : verte = `CMD_WAITING_MQTT`, posté une seule fois juste après un `connect()` MQTT réussi ET des souscriptions saines (pas d'expiration auto, attend un vrai message) ; orange = WiFi `WL_CONNECTED` mais `mqttClient.state()==-2` (échec TCP broker), 1ère fois puis toutes les 60s, plafond 3 ; rouge = `WiFi.status()!=WL_CONNECTED`, même cadence/plafond. Les 3 partagent `MAX_CONNECTION_ALERT_COUNT=3`.

- **Resynchronisation DMD↔RB au démarrage/reconnexion — reposait entièrement sur le retain MQTT passif, un vrai trou trouvé et corrigé (2026-08-23, firmware v123 + `marquee.sh` v17).**
  Investigation demandée par l'utilisateur ("vérifier que le DMD ne repasse pas en playlist alors qu'un jeu est en cours"). Constat : `marquee.sh` publie bien `default`/`system`/`game`/`ingame` en RETENU (`-r`) à chaque transition — un DMD qui se reconnecte reçoit donc normalement le dernier état réel automatiquement (pas de mécanisme de requête active, aucun n'a jamais existé). MAIS 2 trous réels confirmés : (1) le handler `start)` de `marquee.sh` (tourne à CHAQUE redémarrage du script — reboot RB **ou simple crash/relance d'ES pendant qu'une vraie partie tourne déjà**) forçait `default` inconditionnellement, sans jamais vérifier `Action=` dans `/tmp/es_state.inf` (champ écrit par ES lui-même, jamais lu par ce script avant) — fixé en v17 (`Action=rungame` détecté → publie `game`+`ingame=1` comme un vrai `rungame`, pas `default`) ; (2) `marquee/cmd/ingame` était un canal MORT côté firmware depuis v104 (souscription retirée avec l'ancien sous-système hi-score overlay) alors que `marquee.sh` continuait de le publier fidèlement — réabonné en v123 (`g_recalboxInGame`, simple état courant, PAS raccroché à l'ancien overlay), utilisé en 2e ligne de défense dans `CMD_DEFAULT` (un `default` reçu pendant que `g_recalboxInGame` est vrai est ignoré). Persistance mosquitto (`persistence true`) jamais activée sur RB1 (vérifié `/etc/mosquitto/`) — tout redémarrage du broker efface le retain ; jugé hors scope pour l'instant (le fix (1)+(2) couvre le cas réel identifié). **Validé bout-en-bout sur matériel** : `Action=rungame` simulé dans `es_state.inf` + évènement `start` injecté → log confirme `game`+`ingame=1` publiés (pas `default`) ; DMD flashé (v123) confirme en série `[MQTT] marquee/cmd/ingame -> 1` puis bascule correcte sur le marquee du jeu ; `ingame=0` republié → DMD reprend la playlist normalement (`currentMode 1 -> 0`, GIF playlist relancé).

- **Comportement par type de veille RB — les 4 valeurs de `emulationstation.screensaver.type` ne se comportent PAS toutes pareil (2026-08-23, `marquee.sh` v18 + `dmd_score.sh` v28).**
  Investigation demandée par l'utilisateur ("en mode clip & demo afficher marquee + panneaux d'info équivalent au survol de liste du jeu concerné ; garder la playlist pour bouncing/baisse luminosité/écran noir"). Vérifié en conditions réelles sur RB1 (`screensaver.type` forcé successivement sur les 4 valeurs, capture complète du flux `Recalbox/EmulationStation/Event` — **piège de timing** : l'idle timer ne démarre qu'après le règlement complet du menu au boot, ~90-100s après un redémarrage ES, pas juste après le délai configuré dans `screensaver.time` — une fenêtre de capture plus courte donne l'illusion que rien ne se déclenche).
  - **dim/black/bouncing** : un seul évènement `sleep`, jamais répété — comportement INCHANGÉ (playlist via le `sleep)` existant), déjà correct, aucune modif nécessaire (dim vérifié directement, black/bouncing par inférence — même famille d'énumération ES, mêmes réglages "non-demo").
  - **demo** : évènements RÉELS `rundemo`/`enddemo` — **PAS** `startgameclip`/`stopgameclip` comme supposé depuis l'origine du script (ces 2 noms ne se sont JAMAIS déclenchés sur ce matériel — code mort gardé par prudence, coût nul). `es_state.inf` peuple `SystemId`/`GamePath` pendant `rundemo` exactement comme pendant un survol de liste.   - **BUG RÉEL #2 trouvé en testant le fix #1 sur matériel** (pas en théorie) : ES peut enchaîner les jeux demo à ~1/s de façon SOUTENUE pendant plusieurs MINUTES (observé, pas un pic isolé) — publier `game` sans garde a bloqué le DMD indéfiniment sur l'écran d'attente (confirmé : zéro `[MQTT] marquee/cmd/xxx ->` reçu côté DMD pendant 3+ minutes, alors que les topics retenus étaient bien à jour côté broker). Même famille que le rc=-4 déjà documenté (rafale de connexions locales `mosquitto_pub`), mais profil DIFFÉRENT : taux modéré SOUTENU dans la durée, invisible au détecteur de rafale "instantanée" existant (`BURST_THRESHOLD` dans la MÊME seconde — 1/s reste toujours en-dessous). ## Philosophie "DMD bête" (hi-score/infos/description/RA, depuis 2026-08-19/20)

- **Le DMD reste 100% passif — toute décision de timing/logique vit côté script Recalbox (RB), jamais côté firmware.**
  `CMD_GAME`/l'affichage du jeu restent gérés par le DMD comme avant (inchangés). Le contenu hi-score/infos/description/RA est ajouté par-dessus via un canal unique (`marquee/cmd/score`) sans aucune dépendance au canal `marquee/event`/`CMD_STARTCLIP`/`CMD_RESUMESYS` (zone à risque, voir ci-dessus) — retour automatique au jeu par un timer purement LOCAL au DMD (aucun message RB requis pour revenir), garantie anti-blocage explicite. Toute nouvelle fonctionnalité de ce sous-système (répétition périodique, dwell navigation, etc.) doit suivre ce même principe : complexité/état côté RB, DMD strictement dumb-display + auto-revert. Un réglage exprimé en unités "sûres par construction" (ex. répétition en CYCLES de slideshow plutôt qu'en secondes) est préférable à un réglage brut qui oblige l'utilisateur à calculer une valeur sûre à la main.

## Chantier "bucket" — flag "lent" par sous-dossier alphabétique (2026-08-23)

- **Concept porté depuis le worktree `dev-slow-flag-per-bucket`** (firmware v37 / outil PC v29, jamais mergé ni testé sur matériel réel — compilé seulement) vers `dev-core-reassignment` (firmware v124, `RecalBoxDMD_tool.py` v36). Retour utilisateur explicite : "beaucoup de précision et de prudence... aucune des fonctionnalités actuelles ne doit être cassée ou altérée".
  Le flag "lent" (L, déclenche l'écran masque d'attente pendant le chargement d'un jeu) était calculé et stocké **par système entier** (comptage cumulé sur tous les sous-dossiers alphabétiques A..Z/# de `/systems/<sys>/`), pénalisant inutilement un sous-dossier peu peuplé dès que le TOTAL du système dépassait le seuil, même si un seul autre sous-dossier en était responsable. Rendu **par sous-dossier alphabétique (bucket)** : `systems_cache.dat` gagne un 4e champ optionnel (27 caractères 'L'/'N', un par bucket `#ABCDEFGHIJKLMNOPQRSTUVWXYZ`), rétrocompatible dans les 2 sens (un firmware non modifié ignore silencieusement le 4e champ ; un firmware modifié lisant un ancien fichier à 3 champs bascule automatiquement en repli sur le flag système agrégé). Nouvelles fonctions firmware `bucketLetterForFilename()`/`sysBucketSlowFlag()` (2 call sites : `drawPng()`, `CMD_GAME`) ; côté outil PC, `_bucket_letter_for_stem()` factorisée + `build_systems_cache()` compte désormais via `count_ext_over_per_bucket()` (scan non récursif par bucket).
  **Divergence significative depuis le point de départ de la branche source** (tout le travail hi-score/resync/alertes de cette session n'existait pas encore côté bucket) — port manuel, pas un merge/rebase. **Bug réel évité en portant** (absent de la branche source) : `buildSysDefaultCache()` (repli firmware si `systems_cache.dat` absent) ne calcule aucune donnée par bucket mais n'initialisait pas `sysCachePerLetterVals` pour ces entrées — mémoire heap non initialisée (malloc, pas calloc) jusqu'au prochain reboot, `sysBucketSlowFlag()` aurait pu lire un octet parasite. Fix : `memset('?', ...)` explicite ajouté.
  **`slow_threshold` (seuil réglable, onglet Paramètres) ramené de 5000 à 800** (retour utilisateur explicite) : le 5000 n'avait de sens que pour l'ancien calcul agrégé par système entier (évitait de marquer à tort de petits systèmes "lents" à cause d'un seul gros sous-dossier — voir l'historique complet v31→v33 dans `RecalBoxDMD_tool.py`) ; avec le flag L désormais calculé PAR BUCKET, ce problème n'existe plus par construction, 800 (seuil d'origine) redevient pertinent. Changé aux 3 endroits : `RecalBoxDMD_prefs.py` v8 (défaut persisté), `RecalBoxDMD_tool.py` (repli), `RecalBoxDMD_GUI.py` v50 (repli affichage Spinbox).
  **Validé** : firmware compilé OK (65% flash, +976 octets) ; smoke-test offline du comptage par bucket (dossier synthétique bucket S=900/G=15 + 3 résidus "à plat" A/#/Z → ligne générée exacte, seul S marqué L) ; **rétrocompatibilité confirmée EN DIRECT sur matériel** (DMD flashé v124, vrai `CMD_GAME` traité avec l'ancien fichier à 3 champs — log `bucket=J slowFlag=N isSlow=0`, dérivation correcte, repli propre, aucune régression observée). Cas positif (2 buckets d'un même système avec des flags différents, sur un vrai `systems_cache.dat` à 4 champs régénéré par l'utilisateur) laissé à valider lors du prochain usage normal de l'outil.

- **Mode 6/7 de l'outil PC — bouton "choisir dossier" débloqué (RecalBoxDMD_GUI.py v51).** Retour utilisateur : ces 2 modes (génération `games_cache.bin`/`systems_cache.dat` seuls) restaient figés sur `self.sd_dir/"systems"` (dossier de travail temporaire), impossible de les faire pointer directement sur une vraie carte SD externe déjà préparée sans repasser par tout le pipeline Mode 1/2/3. Aucune raison structurelle ne justifiait cette restriction pour Mode 6/7 (contrairement à Mode 2/9/10/11, qui ont une vraie dépendance : téléchargement GitHub ou étape précédente obligatoire) — bouton réactivé, `_pipeline_mode_6()`/`_pipeline_mode_7()` lisent désormais `cfg.roms_root` (dossier choisi) au lieu du chemin figé. La sortie (`games_cache.bin`/`systems_cache.dat`) reste écrite dans le dossier de travail habituel, inchangé — seule l'entrée devient choisissable.

- **2 bugs réels DÉJÀ CORRIGÉS sur `master` mais jamais portés vers `dev-core-reassignment`** (divergée juste avant ces fix, dernier commit commun `450dd26` pour `RecalBoxDMD_GUI.py` / `3d48f31` pour `RecalBoxDMD_tool.py`) — trouvés en cours de route pendant ce chantier, portés avec le même niveau de précision (diff isolé du commit exact sur master, jamais un merge/rebase à l'aveugle) :
  1. **Popup "fin de copie SD" vide** (`RecalBoxDMD_GUI.py` v52, porté depuis master v51-v54, commits `92df16b`→`edac447`) : `_center_toplevel(dlg)` était appelée AVANT le `pack()`/`grid()` des widgets dans `_on_mode6_flash_done()` (le dialogue "Explorer SD/Explorer temp/Fermer") et la popup de nettoyage de `_on_quit_app_clicked()` — calcul de centrage basé sur une fenêtre encore vide (~1x1), perçu comme une fenêtre "vide". Fix complet porté : réordonnancement des 2 call sites + DPI-awareness (`SetProcessDpiAwareness`) + `_clamp_to_root_monitor()` (confine au moniteur réel contenant root, pas juste le moniteur primaire Tk) + fenêtre racine explicitement centrée au lancement (n'avait jamais de position explicite, Tk la plaçait près du coin haut-gauche par défaut).
  2. **Carte SD non détectée** ("cadre de sélection vide, aucun lecteur dedans") (`RecalBoxDMD_tool.py` v37, porté depuis master `88d2f1b`) : `_list_removable_drives()`/`_ex()` reposaient exclusivement sur `wmic.exe`, retiré par défaut sur les builds récents de Windows 11 — `FileNotFoundError` avalée silencieusement par un `except Exception: pass`. Fix porté : nouvelle fonction commune `_query_logical_disks()` interrogeant WMI via `Get-CimInstance` (PowerShell, natif sur toutes les versions de Windows supportées), repli sur l'ancien `wmic` en dernier recours. **Validé en direct** : détecte correctement la vraie carte SD (`H:` RECALBOXDMD, 59.5 GB, FAT32) parmi plusieurs lecteurs vides d'un lecteur multi-cartes.
  **Leçon actée** : avant de traiter un bug comme "nouveau", vérifier s'il n'a pas déjà été résolu sur `master` (`git log -- <fichier>` sur les 2 branches, comparer les points de divergence) — cette branche dev accumule un retard sur des fixes indépendants de son propre travail (hi-score/resync/bucket) simplement parce qu'elle a divergé avant qu'ils soient commités ailleurs.

## Page web de configuration — pièges JS récurrents (2026-08-20)

- **Ne jamais placer un élément interactif (icône, bouton) À L'INTÉRIEUR d'un élément porteur de `data-i18n`.** `applyLang()` fait `el.innerHTML=tr(el.dataset.i18n)` sur chaque élément marqué — ça efface silencieusement tout enfant présent, y compris ajouté après coup. Piège vécu : icône d'aide "?" Bluetooth insérée dans un `<h2 data-i18n="sec_bt">`, effacée à chaque chargement de page. Toujours mettre l'élément interactif en **sibling** (à côté, pas dedans), quitte à wrapper le texte traduit dans un `<span data-i18n>` séparé.
- **Un popup/tooltip en `position:fixed` plein écran (`inset:0`) qui apparaît AU-DESSUS d'une icône hover lui fait perdre son `:hover` CSS** → `mouseleave` se déclenche sans que la souris ait bougé → fermeture → l'icône redevient survolable → `mouseenter` → réouverture → clignotement. Fix : `pointer-events:none` sur le conteneur plein écran, `pointer-events:auto` uniquement sur la boîte de contenu visible (les événements souris traversent jusqu'à l'icône en dessous, qui garde son survol).
- **Le motif brouillon localStorage `g(k,dv)=(draft&&draft[k]!==undefined)?draft[k]:dv`** (4+ pages) doit exclure la chaîne vide, pas seulement `undefined` — un champ nombre momentanément vidé pendant une frappe est sauvegardé tel quel par `saveDraft()` (déclenché sur CHAQUE `input`), et une chaîne vide écrase alors silencieusement la vraie valeur serveur à chaque rechargement. Condition correcte : `draft[k]!==undefined&&draft[k]!==''`.

## CHANTIER OUVERT (2026-08-20) — Le DMD ne se resynchronise pas sur l'état réel de la RB au (re)branchement

**Symptôme rapporté** : au démarrage (après connexion MQTT validée) et après "Reprendre DMD" (bouton web), le DMD ne reflète pas l'état RÉEL de la RB au moment du (re)branchement — il retombe sur la playlist alors que la RB est en jeu ou dans une liste, et/ou reste bloqué sur l'écran "RecalBox connectée" indéfiniment au lieu d'un temps limité.

**Diagnostic établi (pas encore corrigé)** : `MQTT_WAITING_GRACE_MS = 1500` (`RecalBox_DMD.ino`) — fenêtre de grâce qui ignore DÉLIBÉRÉMENT les messages MQTT retenus (`marquee/cmd/system`/`marquee/cmd/game`, publiés avec `-r` par `marquee.sh`) à chaque connexion, pour éviter d'afficher un jeu "périmé" resté accroché d'une session précédente. Problème : cette fenêtre s'arme au moment où `mqttClient.connect()` réussit — qui survient déjà plusieurs secondes après le début du boot (WiFi, NTP, chargement caches, observé ~15-30s dans les logs de cette session) — donc le message retenu arrive quasi systématiquement DANS cette fenêtre de 1.5s et se fait filtrer. Le DMD attend alors passivement un NOUVEAU message MQTT, que la RB n'envoie que sur une navigation active — si la RB est immobile (en jeu ou en liste sans bouger), rien n'arrive jamais.

**Nature du problème** : ce n'est pas un bug ponctuel mais un trou de conception — le DMD ne fait que réagir passivement aux événements RB, il ne demande/reçoit jamais activement "quel est ton état actuel ?" au (re)branchement.

**Pistes à explorer (aucune tranchée)** :

1. Réduire/retirer la fenêtre de grâce sur `system`/`game` spécifiquement (risque : réintroduit l'affichage d'un jeu périmé après une longue coupure DMD — le problème d'origine que cette fenêtre visait à corriger).
2. RB republie activement son état courant à un moment identifiable côté DMD (ex. topic dédié `marquee/status/rb_state` publié par un watcher marquee.sh, lu par le DMD APRÈS l'expiration de sa propre fenêtre de grâce plutôt qu'au moment du retenu initial).
3. Le DMD publie un message "je viens de me connecter" que marquee.sh écoute et auquel il répond immédiatement par l'état courant (round-trip explicite, pas de dépendance au timing du retenu).

**Décision utilisateur (2026-08-20)** : reporté à une prochaine session (pas traité ce soir, 2 crashs TASK_WDT déjà essuyés — voir plus haut). Budget de test dédié sur matériel nécessaire, ne pas traiter à la légère.

## Scripts RB (userscripts) — verrou anti-relance

- **Verrou fichier PID (check-then-write) PROUVÉ INSUFFISANT — verrou `mkdir` atomique désormais le standard.**
  Motif historique `if [ -f "$PIDFILE" ]; then ...; fi; echo $$ > "$PIDFILE"` : la vérification et l'écriture sont deux opérations séparées, donc PAS atomiques. EmulationStation peut déclencher plusieurs invocations du même script dans la même seconde (rafale d'événements, ex. au boot) — toutes peuvent lire "pas de verrou" avant qu'aucune n'ait écrit le sien. Reproduit deux fois sur `dev/core-reassignment` malgré un verrou PID censé déjà corriger le problème : `dmd_achievement[watch].sh` retrouvé en **4 instances simultanées**, `marquee[...].sh` en 2 (2026-08-20).
  **Fix acté** : remplacer par un verrou `mkdir "$LOCKDIR"` (atomique sur ce filesystem/tmpfs — un seul appelant concurrent peut réussir), avec PID écrit à l'intérieur (`$LOCKDIR/pid`) pour détecter un verrou orphelin (process mort) et le récupérer via `rmdir` + nouvelle tentative. Appliqué aux 3 scripts RB : `marquee[...].sh` (v12), `dmd_score[...].sh` (v5), `dmd_achievement[watch].sh` (v3). **Tout nouveau script RB avec verrou anti-relance doit utiliser ce motif dès la création, pas le motif PID-file.**

## Pagination hi-score/infos/description (dmd_score.sh, depuis 2026-08-20)

- **DESCRIPTION : pagination par PHRASES ENTIERES, jamais par découpe fixe de lignes.**
  `send_paginated()` découpe le texte sur `.`/`!`/`?` (les paragraphes, eux, sont déjà détruits en amont par `dmd_game_info.py` qui normalise tous les retours à la ligne du XML en simple espace — seule la fin de phrase reste détectable) puis empile les phrases une à une sur la page en cours tant que ça tient (3 lignes/page, `LINES_PER_PAGE`). Une phrase n'est **jamais** coupée, sauf le seul cas inévitable où elle est à elle seule trop longue pour une page entière (alors étalée sur plusieurs pages consécutives). Plafond de sécurité dédié `MAX_PAGES_DESCRIPTION=5` (séparé de `MAX_PAGES=3` qui reste pour INFOS/hi-score, pagination à taille fixe inchangée) — ellipse `...` ajoutée à la dernière ligne de la dernière page si troncature réelle. Décision explicite utilisateur après itération : d'abord une version "recule vers la ponctuation précédente dans la fenêtre" (rejetée, coupait les pages trop court), puis "avance vers la ponctuation suivante, quitte à dépasser la fenêtre" (retenue).
  **Ne pas revenir à un découpage par nombre de lignes fixe pour DESCRIPTION sans revalider avec l'utilisateur** — c'est un choix de design délibéré, pas un oubli.

- **Interruption inter-pages sur changement de contexte (`state_still_valid()`, dmd_score.sh v13).**
  `round_robin()` ne vérifiait l'état de référence (state_file/expected) qu'ENTRE 2 tours de types de contenu différents, jamais ENTRE LES PAGES d'un même contenu multi-pages en cours d'envoi (chaque fonction de pagination a son propre `sleep()` interne, invisible à `round_robin()`). Symptôme : lancer/quitter un jeu en pleine séquence multi-pages laissait l'ancienne séquence continuer jusqu'à sa fin, mélangée avec la nouvelle. Fix : `state_file`/`expected` transmis en cascade jusque dans les fonctions de pagination, vérifié après chaque `sleep()` interne. **Tout nouveau point d'envoi multi-pages ajouté à ce fichier doit suivre ce même motif** (accepter `sf`/`exp` en derniers paramètres, vérifier après chaque `sleep`) sous peine de réintroduire ce bug.

## Déploiement RB via plink — piège `pkill -f` auto-destructeur

- **`pkill -f '<motif>'` envoyé dans la MÊME commande plink multi-lignes qu'une ligne contenant le nom de fichier LITTÉRAL (sans backslash) se tue lui-même.** Le shell distant qui exécute tout le bloc (`sh -c "<bloc complet>"`) a ce texte dans son PROPRE `argv` — `pkill -f` matche n'importe quel processus dont l'argv contient le motif, y compris son propre parent invocateur. Symptôme : `plink` retourne un code de sortie ~128, **aucune sortie du tout** (le shell distant meurt avant le premier `echo`). Reproduit 2x sur `dev/core-reassignment` (2026-08-20/21) avec `dmd_score[...].sh`.
  **Fix qui marche** : ne jamais combiner `pkill -f <motif-du-script>` et le nom de fichier littéral dans le même appel `plink` — toujours séparer en appels distincts (1: pkill+cleanup seul, 2: cd+relance seul, 3: vérification `ps` seule).

- **Même famille de bug, variante `ps | grep` : `ps -o args -ww | grep -q -- '<motif>'` peut s'auto-matcher.** Trouvé dans `dmd_score.sh` (`challenge_session_active()`, v24, 2026-08-22) : `grep -q -- '--challenge '` voit, dans la sortie de `ps`, SA PROPRE ligne de commande (qui contient littéralement la chaîne cherchée dans ses arguments) — la fonction retournait donc TOUJOURS vrai, même sans processus cible réel, bloquant silencieusement une fonctionnalité entière (round-robin hi-score/infos/description scotché sur un type erroné pour TOUS les jeux). Piège d'autant plus vicieux qu'un test avec un vrai match concurrent (vraie session active en même temps) masque le bug.
  **Fix qui marche** : casser la chaîne littérale dans l'invocation du grep sans changer ce qu'elle matche réellement, ex. `grep -- '[-]-challenge '` au lieu de `grep -- '--challenge '` (bracket expression regex : matche toujours le même texte cible, mais absent littéralement des arguments du grep lui-même). Réflexe à avoir sur TOUT `ps | grep -f`/`pgrep -f` dont le motif recherché pourrait apparaître dans la commande qui fait la recherche elle-même (nom de script, flag caractéristique, etc.).

## Récolte multi-RB (2026-08-23) — 2e machine (Steam Deck/x86) : piège DISPLAY/XDG_RUNTIME_DIR

- **Un lancement direct via SSH (bypass ES, `emulatorlauncher.pyc` invoqué depuis une session SSH nue) segfault presque systématiquement sur une RB x86 (Steam Deck, X11/openbox) si `DISPLAY`/`XDG_RUNTIME_DIR` ne sont pas explicitement exportés — INDÉPENDANT de RB1 (Raspberry Pi, framebuffer/KMS direct, aucun souci équivalent).** Signature : `segfault at ip 0000000000000000` (saut à un pointeur de fonction NULL, `dmesg` montre aussi `Code: Unable to access opcode bytes at 0xffffffffffffffd6` — motif classique d'un code de retour négatif casté en pointeur de fonction et appelé sans vérification, probablement dans l'init GL/EGL du core). Piège vicieux : le TOUT PREMIER lancement d'une session peut réussir par coïncidence (observé 1x), donnant une fausse impression que "ça marche" avant que tout lancement suivant échoue à 100% — ne jamais conclure à la fiabilité sur un seul essai réussi. Confirmé indépendant du jeu (3 jeux différents testés, tous crashent une fois la séquence "cassée"), indépendant d'ES actif ou non, indépendant de la méthode de fermeture (QUIT réseau vs kill brut), indépendant du shader (`--set-shader scanline.glslp` retiré manuellement, crash identique).
  **Cause trouvée** : le process openbox réellement lancé par ES a `DISPLAY=:0` et `XDG_RUNTIME_DIR=/run/user/0` dans son environnement (`/proc/<pid>/environ`) — absents d'une session SSH nue. **Fix validé** (10/10 lancements consécutifs réussis, zéro plantage) : `os.environ["DISPLAY"]=":0"` + `os.environ["XDG_RUNTIME_DIR"]="/run/user/0"` avant tout `subprocess.Popen` d'`emulatorlauncher.pyc`. **Tout script de lancement direct par SSH sur une RB x86/X11 DOIT exporter ces 2 variables** — sur une RB Raspberry Pi/framebuffer (RB1), ce n'est pas necessaire (confirmé, aucun souci observé là-bas).
  Piège opérationnel additionnel rencontré en chemin : après un `reboot`, `/tmp` est vidé (tmpfs) — toute liste de roms/scripts déployés avant doit être re-poussée après un redémarrage, sinon `FileNotFoundError` silencieux côté script (le message d'erreur réel était masqué par un exit code peu clair côté `plink`/PowerShell — toujours vérifier le fichier stdout/log du process plutôt que de se fier au seul code de sortie de la commande de lancement).
  **Architecture RB2 confirmée pour référence future** : `mame`/roms partagés via NAS entre RB (identique à RB1 : 1486 FBNeo, 42503 mame0278), mais **saves (`.hi`) restent locales à chaque machine**, pas de conflit entre récoltes parallèles sur plusieurs RB. `S31emulationstation stop` sur cette machine fait `killall emulationstation` + `killall openbox` (X server mourant en cascade via `startx`, pas d'action directe sur Xorg) — contrairement à RB1, PAS de piège "orphelin survit au stop" observé ici une fois le fix DISPLAY en place.

- **2e bug REEL, PLUS IMPORTANT que le premier (DISPLAY) : ne JAMAIS couper/relancer ES ou Xorg sur une machine x86/X11 (RB2) pour lancer un jeu directement — contrairement à RB1.** RB1 (Raspberry Pi, framebuffer/KMS) a une contrainte materielle reelle d'occupation EXCLUSIVE de l'ecran — ES DOIT y etre coupe avant tout lancement direct, sinon conflit KMS confirme des le debut de cette investigation (voir plus haut). RB2 tourne sous X11 (Steam Deck), concu pour PLUSIEURS clients simultanes — rien n'oblige a y couper ES. ## `dmd_score.sh` — architecture démon MQTT unique (piège opérationnel, 2026-08-23)

- **`dmd_score[rungame,endgame,gamelistbrowsing](permanent).sh` N'EST PAS relancé par ES à chaque événement.** Malgré son nom entre crochets (convention habituelle "ES invoque ce script sur ces événements"), ce script démarre UNE SEULE FOIS (déclenché par le tout premier événement ES après boot), acquiert le verrou singleton (`mkdir /tmp/dmd_score_singleton.lock`), puis reste un **démon persistant unique** abonné en continu à `mosquitto_sub -t Recalbox/EmulationStation/Event` (`while IFS= read -r event`, tout en bas du fichier) — TOUS les événements suivants (rungame/endgame/browsing d'autres jeux) sont reçus par CE MEME process via le flux MQTT, pas par de nouvelles invocations. Toute invocation manuelle ultérieure du script (ex. `sh script.sh rungame` en SSH pour deboguer) voit le verrou deja tenu et sort immediatement SAUF si le vrai démon est mort entre-temps -- dans ce cas l'invocation manuelle devient ELLE-MEME accidentellement LE démon (le script ignore totalement `$1`, seul l'abonnement MQTT compte).
  **Piège vécu ce soir** : un test manuel de debug (`sh script.sh rungame`) a par coincidence hérité du rôle de démon (le vrai avait deja le verrou... en réalité c'est l'inverse -- voir le déroulé complet dans la mémoire projet) puis a été tué en le prenant pour un process de test bloqué -- plus AUCUN événement ES n'a alors été traité jusqu'à ce qu'un reboot complet relance proprement le cycle normal. Symptôme trompeur : semblait un bug de "config mal propagée" (a rappelé a tort le bug de troncature MQTT `marquee/status/features`, sujet distinct) alors que c'était simplement "le démon a été tué et rien ne le relance automatiquement en dehors du cycle de boot normal".
  **A RETENIR pour toute session future de debug sur ce fichier** : avant de tuer un process `dmd_score[...]` trouvé via `ps`, vérifier s'il s'agit bien d'un doublon a nettoyer et PAS de l'unique démon actif -- si un doute existe, préférer un reboot complet (qui relance le cycle ES normal proprement) plutôt qu'un kill manuel suivi d'une tentative de relance manuelle (fonctionne, mais fragile -- voir `start_dmd_score_daemon.sh` dans le scratchpad de session si besoin de reproduire, `setsid nohup ... &disown` necessaire pour survivre a la deconnexion SSH).

## Récolte MAME0278 (RB2) — faible taux de `.hi`, cause identifiée, outillage "vérité d'abord" étendu à la RAM live (2026-08-23)

- **Run complet de la nuit précédente (10:30-11:55, juste après boot RB2) : ~90% d'échecs `retroarch jamais apparu`, y compris sur des jeux "validés 5/5" la veille.** Diagnostic : lancements isolés/tests de charge dans les mêmes conditions mais ~2h après boot → 90-100% de réussite. Cause retenue : état transitoire juste après boot (probablement le montage réseau du partage roms/NAS pas encore stabilisé), PAS un défaut du script v2 ni de la règle "ES jamais coupé" sur RB2. Aucune correction de code nécessaire — juste ne pas lancer une récolte immédiatement après un boot RB2.
- **Cause du faible taux de `.hi` PEUPLÉS (même une fois le taux de lancement à ~100%) : qualité de curation du `hiscore.dat` natif du plugin Lua MAME, pas un problème de méthode.** Le vrai fichier utilisé par le plugin est `/usr/share/libretro-mame/mame0278/plugins/hiscore/hiscore.dat` (18902 lignes — PAS le dossier `bios/<core>/` façon RetroArch classique, qui n'existe même pas pour `mame0278`). Format documenté en tête de fichier : `@<cputag>,<addressspace>,<address>,<length>,<valeur attendue 1er octet>,<valeur attendue dernier octet>,[prefill]` — un mécanisme d'**attente d'initialisation** (le plugin attend que la zone mémoire visée corresponde à ces valeurs avant de commencer à la suivre/sauvegarder). Si l'adresse est fausse, la condition ne se déclenche jamais → aucun `.hi`, silencieusement, quel que soit le temps d'attente.
  **Preuve concrète trouvée** : `batlzone` (le vrai jeu vectoriel Atari Battle Zone, confirmé par capture d'écran montrant le tableau de scores par défaut à l'écran) est rattaché PAR ERREUR au bloc `mayday`/`maydaya`/`maydayb` dans le fichier (adresse `b260`), alors que le vrai driver `bzone`/`bzonea`/`bzonec` (`atari/bzone.cpp`) a sa propre entrée correcte juste au-dessus (`0300,3c,05,38`). Erreur de fusion/curation dans le fichier communautaire, pas un bug du pipeline recalbox/DMD.
- **Preuve que la méthode de récolte (lancement/dwell 15s/`SCREENSHOT`/`QUIT` réseau) n'est PAS en cause** : rejouée sur FBNeo/RB2 (jamais ES coupé) sur `airwolf` (déjà peuplé sur RB1 la veille) → `.hi` régénéré, **octet pour octet identique** à l'original RB1. Le mécanisme de sortie est donc validé sain des deux côtés (FBNeo et MAME) ; le problème est bien spécifique aux données `hiscore.dat` de mame0278.
- **`/usr/share/...` est en lecture seule** (overlay racine monté `ro` sur cette machine, confirmé via `mount`) — impossible d'éditer `hiscore.dat` en place (`OSError: Read-only file system`). **Solution retenue et validée : `mount --bind <copie_corrigée> <chemin_original>`** — superposition temporaire au niveau VFS, ne touche jamais le fichier réel dessous, réversible instantanément par `umount`. Confirmé par test réel : contenu vu par le système bien corrigé pendant le bind-mount, original garanti intact après démontage.
  **Test empirique sur `batlzone`** (hypothèse "même adresse que `bzone`", `0300,3c,05,38`) → **toujours pas de `.hi`**. L'hypothèse "batlzone = simple clone de bzone" est donc fausse (probablement un bootleg avec code réorganisé à une autre adresse) — confirme qu'une correction ne peut PAS être devinée par analogie avec un jeu voisin, il faut la trouver par reverse-engineering réel (RAM live + capture d'écran).
- **Commande réseau RetroArch `READ_CORE_RAM <addr_hex> <n>` (UDP 127.0.0.1:55355) confirmée fonctionnelle sur le core mame0278** — jusqu'à 16384 octets par appel en ~15-20ms (65536 = timeout, à éviter). **MAIS le support dépend du driver MAME** : fonctionne sur du hardware "standard" (`bigstrkba`, `asurabld` confirmés, CPU+RAM classique), répond `-1` (échec, aucune donnée) sur du hardware plus exotique (`batlzone` = générateur vectoriel Atari, `batman` = cabinet multi-carte) — RetroArch n'expose la carte mémoire (`retro_get_memory_map`) que pour certains drivers. Donc la méthode "dump RAM live" ne sera jamais universelle, seulement applicable à un sous-ensemble de jeux (à vérifier au cas par cas).
  **Piège opérationnel réel trouvé en construisant l'outil** : envoyer `SCREENSHOT` puis immédiatement réutiliser LA MÊME socket UDP pour `READ_CORE_RAM` fait avaler par erreur une réponse résiduelle de `SCREENSHOT` par le premier `recvfrom()` du dump → échec de parsing silencieux (0 octet obtenu). **Corrigé : sockets séparées** (une pour les commandes fire-and-forget SCREENSHOT/QUIT, une dédiée au dump RAM).
- **Nouvel outillage créé (2026-08-23)**, en extension de la méthode "vérité d'abord" (`build_entry_from_truth.py`) à la RAM live plutôt qu'à un `.hi` déjà écrit :

## Cycles courts de déconnexion MQTT "3 subscribe() en echec" (2026-08-24) — cause racine identifiée côté broker, PAS un fix trouvé

**Contexte** : retour utilisateur — comportement absent avant les ajouts de cette session (bucket/resync/veille démo-gameclip), symptôme observé même après un reboot RB1 propre (pas juste "le DMD galère"). Enquête complète menée avec instrumentation directe sur matériel (pas d'arithmétique/hypothèse non vérifiée), 3 versions de diagnostic (v128→v130).

- **v128 (delay(0)→delay(1) dans les boucles MODE_GIF/MODE_PLAYLIST)** : hypothèse initiale (contention SD pendant le rendu `gifRawPackMode=1`, `drawGifRaw565Frame()` fait un `SD.read()` par frame, déjà documenté comme "point de contention le plus fréquent... deadlock mqttTask/LWIP" dans un commentaire ANTÉRIEUR à cette session). **Testé en direct, AUCUN EFFET mesurable** — intervalle connect→échec quasi identique (~38.8s) avant et après, sur des contenus différents. Hypothèse invalidée par la mesure, pas juste supposée fausse.
- **v129 (timing fin par tentative de subscribe)** : révèle que les 2 premiers `subscribe()` après `connect()` bloquent chacun ~9-10s **sur les 2 essais** (pas une lenteur qui répond tard — une écriture qui n'obtient jamais de réponse, jusqu'au timeout socket `setSocketTimeout(10)`). - **v130 (état `connected()` juste avant chaque tentative)** : `preConnected=1` juste avant le 1er `subscribe()` qui bloque puis échoue — la connexion se déclare VIVANTE juste avant d'écrire, `postConnected=0` seulement après coup. Le client ne sait pas que la connexion est morte avant d'essayer d'écrire dessus.
- **Cause racine confirmée côté broker (bind-mount temporaire `/etc/mosquitto.d/mqtt.conf` avec `log_dest file`, piège permissions rencontré et corrigé — le fichier doit être écrit par l'utilisateur `mosquit+`, pas root)** : log mosquitto sans ambiguïté —
  ```
  ...614: New client connected ... as esp32-marquee (p2, c1, k15).
  ...639: Client esp32-marquee has exceeded timeout, disconnecting.
  ```
  25s d'écart = timeout keepalive DU BROKER (k15 = keepalive 15s, tolérance MQTT standard 1.5×15=22.5s). Le broker ne reçoit **RIEN DU TOUT** du DMD après le CONNECT initial (ni PING, ni SUBSCRIBE) jusqu'à expiration. **Aucune trace de "kick d'ID client"** (hypothèse v83 déjà présente dans ce fichier, écartée par cette preuve — pas de double-connexion simultanée observée, juste un timeout propre puis un nouveau connect ~49s plus tard).
  **Conclusion** : le chemin d'ÉMISSION WiFi du DMD lui-même se bloque pendant 10-25s juste après un `connect()` réussi, indépendamment du contenu affiché (reproduit hors gameclip aussi, ex. 13:06-13:07). Pas un bug de mosquitto, pas un bug de rendu firmware, pas un bug des scripts RB.

## Crash `abort()`/PANIC firmware (23/08 soir) — enquête complète, PAS causé par bucket/veille/resync

**Contexte** : retour utilisateur explicite après un reboot DMD observé en direct — "on a quand même une série de modifs qui amène ce crash à se produire... il faut enquêter... au lieu de repartir de la base saine et injecter les modifs une par une". - **Mécanisme du crash (confirmé, addr2line + doc ESP-IDF officielle)** : `getNextGifRandom()` → `SD.open()` → `operator new` échoue (heap contigu insuffisant à cet instant précis) → tente de lever `std::bad_alloc` → la construction de l'exception elle-même échoue (`CONFIG_COMPILER_CXX_EXCEPTIONS_EMG_POOL_SIZE=0` dans le SDK précompilé `esp32-libs/3.3.11/sdkconfig`, confirmé — figé, non modifiable depuis l'IDE Arduino) → ESP-IDF abandonne directement (`abort()`) avant même que l'exception ne soit levée, donc n'atteint JAMAIS le `try/catch` existant autour de cet appel (pas un bug de ce try/catch, une limitation de la plateforme). Doc officielle : ESP-IDF C++ Support (docs.espressif.com/projects/esp-idf/en/stable/esp32/api-guides/cplusplus.html).
- **`-fexceptions` EST actif** pour la compilation du sketch (`esp32-libs/3.3.11/flags/cpp_flags`) — l'hypothèse initiale ("exceptions désactivées à la compilation") était FAUSSE, écartée avant de conclure.
- **`maxAllocHeap` reste rigoureusement STABLE (4596) sur toute la fenêtre du crash** (log série, aucune dérive progressive) — le mécanisme n'est PAS un tas qui se dégrade avec le temps/l'usage, c'est une collision ponctuelle entre 2 tâches FreeRTOS concurrentes : `mqttTask()` (reconnexion/subscribe/`broadcastFeatureStatus()`) et `loop()` (avancement playlist, `SD.open()` indépendant) — le crash observé survient <700ms après un `[MQTT] connected`.
- **PREUVE DIRECTE que bucket/CMD_GAME est hors de cause pour CET incident** : zéro trafic `bucket=`/`CMD_GAME` dans le log série DMD sur toute la fenêtre 20:48-20:53 — le DMD ne faisait qu'avancer sa playlist locale (`mode=0`, cycle normal), aucune commande MQTT de jeu reçue.
- **Cause racine réelle trouvée par corrélation avec `marquee_mqtt.log` (RB1)** : `marquee.sh` venait de redémarrer (20:49:43, reboot RB/relance ES) puis ES a balayé la totalité de sa liste de systèmes en interne au démarrage — ~70 `EVENT=systembrowsing` à la suite, ~1/s, pendant plus d'une minute (20:50:25→>20:51:37), chacun republié tel quel en `marquee/cmd/system` (`throttled=0` sur chaque ligne). Ce flux échappait aux 2 garde-fous existants : la fenêtre de grâce boot (10s fixes, largement dépassée) et le détecteur anti-rafale (seuil par seconde d'horloge, ~1/s ne l'atteint jamais quelle que soit la durée). Exactement le même trou architectural déjà trouvé et corrigé pour le mode démo (v18, "BUG REEL #2", voir changelog `marquee.sh`) — mais ce fix n'avait été branché QUE sur `rundemo|startgameclip`, jamais sur `gamelistbrowsing|systembrowsing` où le même trou existait depuis l'origine du fichier (PAS une régression bucket/resync/veille de cette session — un angle mort pré-existant, jamais autant exposé qu'avec un reboot RB1 pendant une session de tests intensifs).
- **Fix appliqué** (`marquee.sh` v20) : fenêtre de grâce boot rendue glissante (`BOOT_TIME` remis à `now` à chaque événement ignoré pendant la grâce, au lieu d'un délai fixe one-shot) — se prolonge tant que les événements arrivent rapprochés (<10s), se termine au premier vrai silence. Aucun impact sur la navigation humaine normale. Déployé + validé en production (banner "v20" confirmé dans le log RB1) — validation complète (observer un vrai reboot RB1 sans le flux non filtré) encore à faire, pas encore observée en conditions réelles post-fix.
- **Facteur mineur confirmé mais pas déterminant** : v123 a ajouté un 13e topic MQTT souscrit (`marquee/cmd/ingame`) — augmente légèrement la durée/surface d'échec du cycle `subscribe()`, mais insuffisant seul pour expliquer l'ampleur du phénomène observé.
- **Conclusion actée** : ne pas revenir sur bucket/resync/veille (aucune preuve ne les implique dans cet incident) — le vrai bug était ailleurs et est maintenant corrigé à la racine. Les symptômes "difficulté de connexion/lenteur" rapportés comme co-occurrents cette même soirée partagent très probablement cette même cause (charge RB1/broker pendant le balayage), pas 3 bugs séparés.

## Lua `autoboot_script` (RB2, MAME0278) — le notifier par frame (`emu.add_machine_frame_notifier`) plafonne à ~150 frames, cause non élucidée (2026-08-25)

**Contexte** : suite de la percée `autoboot_script` (voir section plus haut) — objectif : piloter depuis Lua une séquence credit→start→dwell avec snapshots RAM à chaque étape, pour identifier par diff les adresses score/vies/crédits/continue/stage (demande explicite utilisateur). - **5 hypothèses testées et ÉCARTÉES avec preuve directe, par élimination successive** :
  1. Volume d'E/S du callback (heartbeat toutes les 30 frames) → REJETÉ : retirer le heartbeat n'a PAS repoussé la limite (mort encore plus tôt, avant même la limite observée avec heartbeat).

## Suite immédiate (4) — vérité d'abord sur `inthunt` : START ne prenait jamais effet, bug distinct du credit (2026-08-25)

**Poursuite directe de la demande utilisateur** ("travaille sur les screenshot autant que tu veux"). Captures à `POST_START`/`PLAY_1`/`PLAY_2`/`PLAY_4`/`PLAY_6`/`PLAY_8` sur `inthunt` (le candidat le plus prometteur, `[4,4,5,5,5,5,6,6]`) : **les 6 captures montrent le MEME écran titre** ("CREDIT 01", `1 COIN 1 PLAY`) — le crédit a bien pris effet (visible à l'écran) mais **START n'a JAMAIS déclenché le jeu**, même après les 8 phases de dwell. Le candidat `[4,4,5,5,5,5,6,6]` est donc probablement un compteur d'écran titre (curseur/pulsation), PAS un score.

- **Cause racine trouvée en relisant (à nouveau) le code source du plugin `autofire`** : il **réaffirme `set_value(1)`/`clear_value()` À CHAQUE FRAME** tant que la touche physique est tenue (boucle `process_frame` → `process_button` appelée en continu), PAS un seul appel ponctuel. `hiscore_probe` ne faisait qu'UN SEUL appel `set_value(1)` par appui — suffisant pour un détecteur à FRONT MONTANT (le crédit, généralement edge-triggered → d'où son succès sur tous les jeux), insuffisant pour un bouton lu comme MAINTENU sur plusieurs frames (le comportement de `1 Player Start` sur ce driver, et potentiellement d'autres).
- **Fix (`hiscore_probe` v0.0.4)** : nouvelle action `hold` (remplace `press`/`release`) — liste de "holds actifs", `set_value(1)` réaffirmé CHAQUE frame tant que le hold est actif, `clear_value()` une seule fois à l'expiration. `START` tenu 60 frames (1s) au lieu d'un pulse de 6 frames.
- **Revalidé sur `inthunt` par capture réelle** : `PLAY_8` montre maintenant un VRAI écran de jeu (cinématique de mission "URGENT COMMAND...") avec HUD réel (`1P 00000000`, `CREDIT 00`) — START a fonctionné, le score réel est confirmé à 0 (aucun tir automatique dans la séquence actuelle, cohérent). Les anciens "candidats score" de ce jeu sont bien écartés (bruit d'animation de cinématique, pas un score qui n'a jamais bougé).
- **Portée** : ce bug affectait potentiellement TOUS les jeux du lot précédent, pas seulement `inthunt` — plusieurs jeux "réussis" plus tôt dans cette session pourraient en réalité ne jamais avoir dépassé l'écran titre (le `credit_diff`/les candidats observés seraient alors, comme ici, des artefacts d'écran titre plutôt qu'une vraie partie). **Reprise complète du lot des 16 jeux nécessaire avec v0.0.4 avant de considérer un seul candidat comme fiable.**
